# Renderer resilience output validation

## Goal

Make the media render stage robust, deterministic, and diagnosable for supported GoPro source variations. Given a valid `HighlightPlan`, the renderer must execute the planned intervals in chronological order, preserve the existing HUD appearance, produce a readable MP4 with safe audio/timestamps, and fail the job explicitly when its output is invalid.

## Scope

This feature hardens the existing per-segment FFmpeg render and concat pipeline. It does not redesign the HUD, minimap, event feed, collectible behavior, `GameEvent` contract, highlight planning, synchronization, `coins.json`, or selection workflow.

The supported input profile remains readable original GoPro MP4 chapters with a usable video stream, including the H.264/HEVC variants that the installed FFmpeg can decode, normal GoPro dimensions/frame rates, and optional audio. GPMF/GPS5 remains required upstream when synchronization is needed. The feature will not introduce a speculative source-transcoding pipeline or broad new media-format support.

## Current architecture

1. `src/video.ts` resolves deterministic highlight-plan intervals and their event IDs.
2. FFprobe reads source stream and format metadata; GPMF timing is probed separately in `src/gpmf.ts`.
3. For each interval, FFmpeg applies the existing HUD/effect filter graph and writes a temporary H.264, yuv420p, AAC, 48 kHz, stereo MP4 segment.
4. Segment files follow plan index order and are joined by the FFmpeg concat demuxer using stream copy.
5. HUD frame sequences are generated by `src/hud/hudRenderer.ts`.

The completed feature must retain this visual pipeline while making the media contract, timeline normalization, final validation, error semantics, diagnostics, and cleanup explicit.

## Decisions

- The renderer consumes `HighlightPlan` as the sole source of segment order; it must not reorder events independently.
- The renderer rejects malformed plans rather than clamping them. Planner clamping remains the planner's responsibility.
- Sources without audio produce a valid generated/silent AAC track, including existing HUD chimes, so all segments share one audio-capable concat path.
- An empty `HighlightPlan` fails clearly and produces no MP4. It does not succeed as a no-op or render the full source.
- Invalid, unsupported, unreadable, or validation-failing output causes a failed job, never silent partial success.
- Raw FFmpeg commands, stderr, and raw probe data stay in logs/debug output. Normal job responses receive only compact diagnostics.
- Large real GoPro media remains external; automated coverage generates tiny temporary fixtures.

## Implementation plan

1. Introduce an internal normalized `MediaInfo` derived from the existing FFprobe result. It will contain source duration, dimensions, optional frame rate/pixel format, video codec, and audio presence/codec/sample rate/channel count. Reuse the existing probe/command utilities and validate the supported source profile before expensive rendering.
2. Validate each planned segment before starting FFmpeg: finite timestamps, non-negative start, strictly positive duration, end within source duration subject only to a narrow floating-point tolerance, ordered/non-overlapping intervals, and preserved non-empty event IDs.
3. Keep the existing HUD and effect filters, while making per-segment video/audio timelines start near zero. Ensure source audio, generated silent audio, unusual input audio timestamps, and encoded segment settings remain concat-safe.
4. Preserve deterministic segment-index ordering and formalize concat behavior for one, two, and many segments without independently sorting the input.
5. Add an internal `RenderValidationResult` with validity, expected/actual duration, duration error, video/audio presence, warnings, and errors. Probe the final MP4 and require a nonempty readable file, video stream, positive dimensions/duration, a timeline near zero where available, required audio behavior, and duration within a documented encoding/container tolerance of the sum of planned intervals.
6. Map relevant failures into the existing job error/status model using clear categories only where they correspond to real failure boundaries: invalid plan, unsupported media, segment render, concat, and output validation. Record a compact render summary with status, segment count, durations, audio, warnings, elapsed time, and optional speed ratio.
7. Ensure each job owns an isolated temporary directory, temporary segments are cleaned on success and practical failure paths, original uploads remain untouched, and the completed output survives cleanup.
8. Document the verified source profile, audio contract, output guarantees, and diagnostic/failure behavior in related feature documentation.

## Acceptance criteria

1. Source media is represented by normalized `MediaInfo`.
2. Invalid plans fail before FFmpeg runs.
3. Audio-bearing and silent sources both render successfully; silent sources produce generated AAC audio.
4. Segments concatenate in exactly `HighlightPlan` order with safe normalized timelines.
5. The final MP4 is automatically FFprobed and validated.
6. Expected output duration is compared to actual duration using a non-frame-perfect tolerance.
7. Invalid output fails the job and emits useful structured diagnostics.
8. Temporary files are isolated and safely cleaned without removing the final output or source upload.
9. Existing known-good visual output remains visually equivalent.
10. No large source-media fixture is committed.

## Validation strategy

Add focused unit tests for normalized inspection, source/profile validation, plan validation, duration tolerance, and validation-result errors. Add generated-FFmpeg integration fixtures under test temporary directories covering:

- H.264 MP4 with and without audio;
- 30 fps and 60 fps at at least two small resolutions;
- HEVC only when current tooling reliably supports it;
- one segment, ordered multiple segments, short segments, adjacent/merged intervals, and source-start/source-end intervals;
- no highlights, which must fail explicitly;
- final stream/dimension/readability/duration assertions, recognizable source-interval ordering, and cleanup after success plus a representative failure.

Generated fixtures must fail transparently if the FFmpeg build lacks a claimed encoder. The implementation will run the smallest relevant existing test/build commands after changes.
